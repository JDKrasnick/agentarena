# Trusted Evidence-Handoff v2

Status: accepted MVP contract

Scope: reviewer-to-attacker handoff only

Implementation tracking: GitHub issues #18, #19, #20, and #58

## 1. Purpose

The trusted evidence handoff is the only review artifact that an attacker may
consume. It carries a compact, ordered set of reviewer hypotheses and the
harness attestations needed to prove that those hypotheses still refer to the
attacker's assigned target and permission policy.

This document is normative. The key words **MUST**, **MUST NOT**, **SHOULD**,
and **MAY** have their usual requirements-language meanings. Issue #18 owns the
schema and persisted artifacts, #19 owns prompt and runtime behavior, and #20
owns telemetry. Those implementations must follow this contract rather than
make new policy choices.

A packet is not an adjudication and no finding is a defect until the judge
establishes canonical defect identity. A packet never contains raw transcripts,
private reasoning, provider identity, secrets, credentials, or the raw frozen
patch.

## 2. Terms and trust boundary

- **Harness** means deterministic Agent Arena code. It captures artifacts,
  computes hashes, validates schemas, invokes adapters, and records lifecycle
  events.
- **Reviewer** means the contestant invocation performing read-only review of
  one frozen target.
- **Attacker** means the later invocation of that same contestant that consumes
  the packet and may construct attacks.
- **Lane** means one reviewer slot, target slot, and round tuple.
- **Target snapshot** means the base commit, frozen implementation patch bytes,
  and resulting frozen Git tree assigned to the lane.
- **Attestation** means a value the harness directly computes or captures.
- **Hypothesis** means any reviewer-authored observation, inference, expected
  behavior, confidence, or test proposal. Inclusion in a harness-signed or
  digest-bound artifact does not promote it to an attestation.

The packet has two trust domains:

| Domain                             | Owner                           | Trust                 | Permitted content                                                                 |
| ---------------------------------- | ------------------------------- | --------------------- | --------------------------------------------------------------------------------- |
| Envelope identity and attestations | Harness                         | `harness_attested`    | IDs, digests, lane identities, snapshot facts, policy fingerprint, omission facts |
| `findings` content                 | Reviewer, normalized by harness | `reviewer_hypothesis` | Structured claims and focused test guidance                                       |

The harness MUST NOT describe a model assertion as harness-attested merely
because it parsed, normalized, persisted, or hashed that assertion. The judge
MUST determine task support, canonical defect identity, severity, and scoring
from submitted attacks and admissible evidence, not from finding IDs or review
confidence.

## 3. Canonical JSON and digest rules

All hashes in this contract use SHA-256 and lowercase hexadecimal output.
Canonical JSON means the JSON Canonicalization Scheme (JCS, RFC 8785): UTF-8,
no insignificant whitespace, lexicographically sorted object keys, JCS number
serialization, and array order preserved. Inputs MUST first pass the strict
schema; implementations MUST NOT rely on lossy coercion before canonicalizing.
Duplicate JSON object keys, non-Unicode input, lone surrogates, non-finite
numbers, and integers outside the schema's safe range are invalid.

The notation `sha256-jcs(value)` means SHA-256 over the canonical UTF-8 bytes of
`value`. A `Sha256` value is exactly 64 lowercase hexadecimal characters. Git
object IDs remain lowercase hexadecimal in the repository's native hash
length; the MVP accepts 40-character SHA-1 and 64-character SHA-256 Git IDs.

The harness computes these values:

```text
target_fingerprint = sha256-jcs({
  "base_commit": base_commit,
  "frozen_git_tree_id": frozen_git_tree_id,
  "frozen_patch_sha256": frozen_patch_sha256
})

permission_manifest_fingerprint = sha256-jcs(resolved_permission_projection)

finding_id = "finding_" + sha256-jcs({
  "target_fingerprint": target_fingerprint,
  "finding": canonical_finding_payload
})

packet_digest = sha256-jcs(packet with packet_digest omitted)
```

`frozen_patch_sha256` hashes the exact persisted patch artifact bytes, without
newline conversion. `frozen_git_tree_id` is the Git tree produced by applying
that patch to `base_commit`; dirty or untracked reviewer changes are excluded
because review is read-only. `packet_id` is a fresh UUIDv7 generated by the
harness for each packet creation or refresh and is included in `packet_digest`.
Therefore two otherwise identical refreshes have different packet identities
and digests.

### 3.1 Resolved permission projection

The permission fingerprint covers the complete resolved policy, not a display
summary. The harness constructs this projection:

```json
{
  "capabilities": [
    {
      "capability_id": "postgres_test",
      "status": "approved",
      "requirement": "optional",
      "roles": ["harness_only"],
      "scopes": ["database:arena", "network:127.0.0.1:5432"],
      "enforcement": "brokered",
      "expires_at": "2026-08-18T21:00:00Z"
    }
  ],
  "reduced_validation": {
    "accepted": false,
    "assessment_digest": null,
    "omitted_check_ids": []
  }
}
```

Capabilities are sorted by `capability_id`; `scopes` and
`omitted_check_ids` are de-duplicated and sorted by Unicode code point. Status
is one of `approved`, `denied`, `unavailable`, `provisioning_failed`, or
`expired`; requirement is `required` or `optional`; `roles` contains exactly
one of `agent`, `harness_only`, or `both`; enforcement is `enforced`,
`brokered`, or `advisory`. The harness derives status from the authoritative
capability decision and current resolved lease:

| Capability decision   | Resolved lease                        | Projected status      |
| --------------------- | ------------------------------------- | --------------------- |
| `approved`            | No lease or an unexpired active lease | `approved`            |
| `approved`            | Expired                               | `expired`             |
| `denied`              | None                                  | `denied`              |
| `unavailable`         | None                                  | `unavailable`         |
| `provisioning_failed` | None                                  | `provisioning_failed` |

A non-approved decision with a lease is an invalid runtime invariant, not a new
projection state. `expires_at` is the resolved lease expiry in RFC 3339 UTC form
or `null`; the harness evaluates expiry with its current clock whenever it
constructs or recomputes the projection. Reduced-validation acceptance, its
exact assessment digest, and all omitted check IDs are mandatory even when
empty. Authentication material, tokens, and credential values MUST NOT enter
the projection.

Any change to a status, requirement, role, scope, enforcement level, expiry,
reduced-validation decision, assessment digest, or omitted check changes the
fingerprint. Policy display labels and redacted provisioning diagnostics do not.

## 4. Packet envelope

The persisted and injected value is one strict JSON object. Unknown fields are
invalid at every level.

```json
{
  "version": 2,
  "packet_id": "0191a2b3-c4d5-7e6f-8123-456789abcdef",
  "packet_digest": "7b44fd04fdcda5af34dfef06b63d7ea5e05cfa0b97769dadd049aec9224d1020",
  "run_id": "run_2026-08-18T200000Z",
  "round_id": "round_2",
  "reviewer_slot": "a",
  "target_slot": "b",
  "target_snapshot": {
    "base_commit": "1111111111111111111111111111111111111111",
    "frozen_patch_sha256": "2222222222222222222222222222222222222222222222222222222222222222",
    "frozen_git_tree_id": "3333333333333333333333333333333333333333",
    "fingerprint": "4444444444444444444444444444444444444444444444444444444444444444"
  },
  "permission_manifest_fingerprint": "5555555555555555555555555555555555555555555555555555555555555555",
  "findings": [],
  "omitted_findings": {
    "count": 0,
    "entries": []
  }
}
```

The values above illustrate shape; examples in section 11 describe validation
outcomes without treating repeated hexadecimal digits as computed fixtures.
Issue #18 MUST add executable digest fixtures generated from the schema.

### 4.1 Envelope field contract

| Field                             | Owner and trust     | Canonicalization                   | Validation                                                                                                                   | Disclosure                                          |
| --------------------------------- | ------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `version`                         | Harness, attested   | Integer                            | Exactly `2`                                                                                                                  | Attacker and local artifacts                        |
| `packet_id`                       | Harness, attested   | Lowercase canonical UUID text      | Fresh UUIDv7; never reused                                                                                                   | Attacker and local artifacts                        |
| `packet_digest`                   | Harness, attested   | `Sha256`                           | Recompute with this field omitted; exact match                                                                               | Attacker and local artifacts                        |
| `run_id`                          | Harness, attested   | Exact persisted identifier         | 1–128 printable ASCII bytes; must equal active `RunSpec` run                                                                 | Attacker and local artifacts                        |
| `round_id`                        | Harness, attested   | Exact persisted identifier         | 1–64 printable ASCII bytes; must equal active round                                                                          | Attacker and local artifacts                        |
| `reviewer_slot`                   | Harness, attested   | Exact stable slot ID               | 1–32 lowercase ASCII letters, digits, `_`, or `-`; must be active lane reviewer; never provider name                         | Attacker and local artifacts                        |
| `target_slot`                     | Harness, attested   | Exact stable slot ID               | Same syntax as reviewer; must be active lane target and differ from reviewer except a topology explicitly allowing otherwise | Attacker and local artifacts                        |
| `target_snapshot`                 | Harness, attested   | Object shown in section 3          | All components must equal frozen lane artifacts and fingerprint must recompute                                               | Attacker and local artifacts; patch bytes excluded  |
| `permission_manifest_fingerprint` | Harness, attested   | `Sha256`                           | Must recompute from current resolved projection                                                                              | Attacker and local artifacts; credentials excluded  |
| `findings`                        | Reviewer hypotheses | Array order is reviewer priority   | Zero to 12 valid, unique canonical payloads after duplicate rejection                                                        | Same contestant's attacker and local artifacts only |
| `omitted_findings`                | Harness, attested   | Entries in original priority order | Count equals entry length; every removal recorded once                                                                       | Attacker and local artifacts                        |

The packet contains no timestamps. Invocation timestamps remain in surrounding
run telemetry so clock formatting cannot affect packet identity.

### 4.2 Omission field contract

All omission fields are harness-owned and `harness_attested`; they are
disclosed to the same attacker and retained in local artifacts.

| Field                         | Canonicalization                    | Validation                                                                                                      |
| ----------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `omitted_findings.count`      | Integer                             | 0–12 and exactly `entries.length`                                                                               |
| `omitted_findings.entries`    | Array sorted by `original_priority` | One entry for every duplicate, over-limit, or size-compacted finding and no others                              |
| `entries[].finding_id`        | Formula in section 3                | Must recompute from the omitted normalized payload and current target fingerprint                               |
| `entries[].original_priority` | Integer                             | Original positive review position; unique except exact duplicates may share only a finding ID, never a priority |
| `entries[].reason`            | Literal enum                        | `duplicate`, `finding_limit`, or `packet_size`                                                                  |
| `entries[].duplicate_of`      | Finding ID or `null`                | Equal to a retained ID exactly when reason is `duplicate`; otherwise `null`                                     |

## 5. Finding contract

Each finding has this shape:

```json
{
  "finding_id": "finding_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "priority": 1,
  "trust": "reviewer_hypothesis",
  "invariant": "Concurrent refresh must preserve the newest valid token.",
  "observations": [
    {
      "trust": "reviewer_hypothesis",
      "statement": "Both requests can read the same pre-refresh version.",
      "provenance": {
        "kind": "code_inspection",
        "references": ["src/session.ts:88-112"]
      }
    }
  ],
  "code_locations": [
    {
      "path": "src/session.ts",
      "line_start": 88,
      "line_end": 112,
      "symbol": "refreshSession"
    }
  ],
  "trigger_sequence": [
    "Start two refresh requests for one session.",
    "Allow both reads to finish before either write.",
    "Complete the writes in reverse order."
  ],
  "oracle": {
    "expected_behavior": "The session retains the token from the newest successful refresh.",
    "task_source_ids": ["source_issue_241"],
    "task_source_rationale": "Acceptance criterion 3 requires concurrent refresh to retain the valid token."
  },
  "confidence": 84,
  "required_capability_ids": ["shell", "filesystem"],
  "regression_test_plan": {
    "summary": "Add a controlled two-request schedule test.",
    "suggested_paths": ["test/session-refresh-race.test.ts"],
    "focused_command": "npm test -- test/session-refresh-race.test.ts"
  }
}
```

`canonical_finding_payload` contains every field above except `finding_id` and
`priority`. Priority is ordering metadata and does not change finding identity.
The literal `trust` fields are included so observations cannot lose their
hypothesis label when projected independently.

### 5.1 Finding field contract

| Field                                  | Owner and trust                              | Canonicalization                                       | Validation                                                                                                     | Disclosure                        |
| -------------------------------------- | -------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `finding_id`                           | Harness, attested identifier of a hypothesis | Formula in section 3                                   | Exact recomputation; it is not a canonical defect ID                                                           | Attacker and local artifacts      |
| `priority`                             | Reviewer, hypothesis metadata                | Integer                                                | Original one-based position, 1–12, unique and ascending in emitted `findings`; never renumbered after omission | Attacker and local artifacts      |
| `trust`                                | Harness normalization of reviewer content    | Literal string                                         | Exactly `reviewer_hypothesis`                                                                                  | Always disclosed with finding     |
| `invariant`                            | Reviewer, hypothesis                         | NFC string, trim outer whitespace                      | 1–1,000 UTF-8 bytes; no control characters except newline                                                      | Attacker and local artifacts      |
| `observations`                         | Reviewer, hypotheses                         | Preserve order                                         | 1–8 entries                                                                                                    | Attacker and local artifacts      |
| `observations[].trust`                 | Harness normalization                        | Literal string                                         | Exactly `reviewer_hypothesis`                                                                                  | Always disclosed with observation |
| `observations[].statement`             | Reviewer, hypothesis                         | NFC and outer trim                                     | 1–1,000 UTF-8 bytes                                                                                            | Attacker and local artifacts      |
| `observations[].provenance.kind`       | Reviewer, hypothesis metadata                | Literal enum                                           | `code_inspection`, `task_source`, `test_inspection`, `tool_summary`, or `other`                                | Attacker and local artifacts      |
| `observations[].provenance.references` | Reviewer, unverified references              | NFC, outer trim, preserve order                        | 1–8 unique strings, each 1–300 UTF-8 bytes; no transcript or secret references                                 | Attacker and local artifacts      |
| `code_locations`                       | Reviewer, hypotheses                         | Normalize paths to target-relative `/`; preserve order | 1–8 unique locations; no absolute path or `..`; positive lines and `line_end >= line_start`; nullable symbol   | Attacker and local artifacts      |
| `trigger_sequence`                     | Reviewer, hypothesis                         | NFC and outer trim; preserve order                     | 1–12 nonempty steps, each at most 500 UTF-8 bytes                                                              | Attacker and local artifacts      |
| `oracle.expected_behavior`             | Reviewer, hypothesis                         | NFC and outer trim                                     | 1–1,500 UTF-8 bytes                                                                                            | Attacker and local artifacts      |
| `oracle.task_source_ids`               | Reviewer, unverified references              | De-duplicate and sort                                  | 1–8 IDs that exist in frozen `RunSpec`                                                                         | Attacker and local artifacts      |
| `oracle.task_source_rationale`         | Reviewer, hypothesis                         | NFC and outer trim                                     | 1–1,500 UTF-8 bytes; must explain support rather than merely name an ID                                        | Attacker and local artifacts      |
| `confidence`                           | Reviewer, hypothesis                         | Integer                                                | 0–100 inclusive; never used for scoring                                                                        | Attacker and local artifacts      |
| `required_capability_ids`              | Reviewer, hypothesis                         | De-duplicate and sort                                  | 0–16 known capability IDs; absence means no capability beyond ordinary approved repository inspection          | Attacker and local artifacts      |
| `regression_test_plan.summary`         | Reviewer, hypothesis                         | NFC and outer trim                                     | 1–1,500 UTF-8 bytes                                                                                            | Attacker and local artifacts      |
| `regression_test_plan.suggested_paths` | Reviewer, hypothesis                         | Normalize target-relative paths; de-duplicate and sort | 0–8 paths; no absolute path or `..`                                                                            | Attacker and local artifacts      |
| `regression_test_plan.focused_command` | Reviewer, hypothesis                         | NFC and outer trim                                     | String or `null`, at most 1,000 UTF-8 bytes; proposal only, never executed without attack validation           | Attacker and local artifacts      |

NFC normalization occurs before IDs and digests are computed. Newlines inside
strings normalize to LF. The harness MUST reject prohibited content rather than
silently redact it because redaction would change the hypothesis. In
particular, provenance may summarize tool output but MUST NOT embed raw command
logs, transcripts, model deliberation, credentials, environment values, or
provider identity.

## 6. Duplicate rejection and size compaction

Review parsing preserves the first 12 submitted positions and assigns their
one-based positions as priorities. Invalid findings are review-schema failures
handled by the review retry policy and never enter a packet.

For valid findings, the harness performs these steps exactly:

1. Normalize each canonical finding payload and compute its `finding_id`.
2. Walk findings in ascending priority. Keep the first occurrence of each
   `finding_id`. For every later exact duplicate, append an omission entry with
   reason `duplicate`, the duplicate's original priority, and
   `duplicate_of` equal to the retained ID. Do not perform fuzzy, semantic,
   embedding, textual-similarity, or canonical-defect deduplication.
3. If more than 12 valid positions somehow reach this boundary, keep positions
   1–12 and record every later entry as `finding_limit`. A conforming review
   parser normally prevents this case.
4. Build the full packet and serialize it as canonical UTF-8 JSON, including
   the final `packet_digest`. The maximum is 16 KiB (16,384 bytes).
5. While the packet is oversized, remove the lowest-priority retained finding,
   append a `packet_size` omission entry, recompute the digest, and measure
   again. Omission entries are finally sorted by original priority.
6. If the review originally contained at least one nonduplicate valid finding
   and no retained finding fits, do not emit an empty packet. Return
   `handoff_blocked` with category `packet_size` and enter the targeted review
   refresh path. A genuinely empty review remains a valid empty packet.

The omission object is:

```json
{
  "count": 2,
  "entries": [
    {
      "finding_id": "finding_bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
      "original_priority": 4,
      "reason": "duplicate",
      "duplicate_of": "finding_bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"
    },
    {
      "finding_id": "finding_cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
      "original_priority": 12,
      "reason": "packet_size",
      "duplicate_of": null
    }
  ]
}
```

`reason` is `duplicate`, `finding_limit`, or `packet_size`.
`duplicate_of` MUST equal the retained finding ID only for `duplicate` and MUST
be `null` otherwise. `count` MUST equal `entries.length`. Omitted findings are
not injected elsewhere or carried to later rounds.

## 7. Creation, validation, and invalidation

The harness creates exactly one current packet for each target lane in each
round after freezing the target and resolving permissions. A refresh supersedes
that packet with a new `packet_id`; it does not create an additional consumable
packet. Packets never carry across rounds.

Immediately before invoking the attacker, the harness MUST:

1. Validate the strict schema, canonical encoding, packet digest, finding IDs,
   duplicate outcome, omission metadata, finding limit, and 16 KiB ceiling.
2. Recompute the target snapshot from the assigned worktree and persisted
   frozen patch.
3. Recompute the complete resolved permission projection and fingerprint.
4. Confirm run, round, reviewer, and target identities against the active lane.

A target or permission mismatch returns `packet_stale`, with diagnostic code
`target_fingerprint_mismatch` or `permission_fingerprint_mismatch`. Any other
packet validation failure returns `packet_malformed`. The attacker is not
invoked. The failed packet and exact diagnostic code are persisted, and the
harness performs one targeted reviewer
refresh for this pre-invocation validation stage. The refreshed review receives
the current target and policy plus only the validation diagnostic needed to
produce a new packet; it does not receive attacker output. If refreshed
validation fails for any reason, the lane ends in coverage loss. There is no
third review attempt and no judge fallback for a missing handoff.

Repair, any target worktree mutation, a new frozen patch, base or tree change,
permission status/role/scope/enforcement/expiry change, or reduced-validation
change immediately invalidates an unconsumed packet. Invalidation is recorded
even if the resulting fingerprints would later return to their old values. A
new round or post-repair review MUST create a new packet; the old packet MUST
never be revalidated and reused.

Prior adjudicated results survive through the versioned, lane-safe
`ContestantFeedback` projection. They MUST NOT be copied into a later handoff as
findings or used to resurrect an old packet.

Normal attacker context contains only that lane-safe projection and the current
active packet. Diagnostic drill-down is permitted only for a stale, malformed,
or blocked handoff. It MUST resolve exactly one directly referenced diagnostic
artifact, MUST stop after that artifact without following nested pointers, and
MUST reject content above 8 KiB. These pointers and lifecycle records are
internal artifacts; this contract adds no report section, observatory element,
or human-facing drill-down control.

## 8. Attacker consumption and blockers

The attacker must return exactly one of these mutually exclusive v2 results:

```json
{ "version": 2, "attacks": [] }
```

or a normal nonempty `attacks` result defined by `AttackSubmissionV2`, or:

```json
{
  "version": 2,
  "handoff_blocker": {
    "finding_ids": [
      "finding_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    ],
    "category": "permission_unavailable",
    "explanation": "The proposed schedule test requires the harness-only database lease, which is expired.",
    "requested_capability_ids": ["postgres_test"],
    "requested_context": []
  }
}
```

A blocker MUST contain no `attacks` key or attack content. Its finding IDs must
contain 1–12 unique IDs in the consumed packet. `category` is one of
`permission_unavailable`, `cited_context_missing`, `target_artifact_unavailable`,
or `policy_ambiguous`. Explanation is a trimmed 1–1,500-byte hypothesis string.
Requested capability IDs must exist in the current manifest; requested context
is 0–8 target-relative file paths or frozen task-source IDs. Credentials,
provider identity, private reasoning, and broad requests such as “the whole
repository” are invalid blocker content.

All blocker fields are attacker-owned, `attacker_untrusted`, and disclosed only
to the targeted reviewer refresh and local run artifacts. They are NFC- and
LF-normalized before validation; arrays preserve order unless stated otherwise.

| Field                                      | Canonicalization      | Validation                                                                                     |
| ------------------------------------------ | --------------------- | ---------------------------------------------------------------------------------------------- |
| `version`                                  | Integer               | Exactly `2`                                                                                    |
| `handoff_blocker.finding_ids`              | De-duplicate and sort | 1–12 IDs present in the consumed packet                                                        |
| `handoff_blocker.category`                 | Literal enum          | One of the four categories above                                                               |
| `handoff_blocker.explanation`              | Trim outer whitespace | 1–1,500 UTF-8 bytes; no prohibited private or secret content                                   |
| `handoff_blocker.requested_capability_ids` | De-duplicate and sort | 0–16 IDs present in the current resolved manifest                                              |
| `handoff_blocker.requested_context`        | De-duplicate and sort | 0–8 target-relative paths or frozen task-source IDs; no absolute path, `..`, or broad wildcard |

A valid blocker consumes no attack ranks, causes no recoil or damage, and marks
the lane's handoff-consumption stage blocked. The harness gives the reviewer one
targeted blocker refresh containing the blocker, the same still-frozen target,
and the current resolved policy. This is a separate stage retry from the
pre-invocation validation refresh. The reviewer may clarify findings, remove
unsupported findings, or produce a genuinely empty packet, but cannot change
the target or policy. The harness validates the fresh packet and invokes a fresh
attacker once. A second blocker, invalid blocker, missing response, or failed
refresh causes coverage loss. It never becomes a miss and never reaches the
judge.

`{"version":2,"attacks":[]}` is successful consumption. It means no packet
hypothesis became credible executable evidence. It completes the required lane
with downstream evidence, execution, adjudication, and repair stages not
applicable. It is distinct from a stale, malformed, oversized, blocked, timed
out, or missing handoff and has no score effect.

## 9. Prompt and inspection policy

The attack prompt is assembled in this order:

1. Standardized public lane context and lane-safe prior feedback.
2. The canonical v2 packet, byte-for-byte.
3. Attack instructions and the `AttackSubmissionV2` output schema.

No content may appear between the packet and attack instructions. The prompt
MUST NOT include the raw frozen patch, reviewer transcript, provider identity,
or private reasoning. The attacker inspects the already-frozen target in its
assigned worktree. The packet digest and target fingerprint are included in
invocation metadata so replay can prove which handoff was consumed.

The attacker may inspect cited files, suggested test paths, nearby tests, and
direct dependencies needed to construct a focused reproducer. This is guidance,
not a read boundary. Broad repository rediscovery is allowed but measured and
receives one non-blocking warning from the adapter when observable. It MUST NOT
be blocked, scored, charged as recoil, treated as a retry, or treated as
coverage loss.

For telemetry classification:

- `targeted`: available adapter observations show only reads/searches confined
  to packet-cited files, suggested test paths, tests in the same directory or
  repository test mirror for a cited basename, direct one-edge imports or
  importers of those files, and repository instruction/build manifests needed
  to run the focused command.
- `broad`: available observations show at least one repository-root recursive
  listing/search or inspection outside the targeted set before attack output.
- `unknown`: the adapter cannot observe enough file/search activity to decide.

If any observable operation is broad, classification is `broad`; otherwise it
is `targeted` only with complete adapter visibility, and `unknown` in every
other case. The record includes classification, adapter visibility
(`complete`, `partial`, or `none`), the packet digest, and whether the advisory
warning was emitted. It MUST NOT include command arguments or file contents
that could expose secrets. Telemetry cannot affect health, damage, recoil,
attack validity, retry eligibility, coverage, confidence qualification, or
selection. Missing visibility is `unknown` without warning or penalty.

Whether warnings change behavior and whether enforceable read boundaries are
practical are explicitly deferred to issue #58. Issue #20 implements the
measurement above but does not evaluate or enforce it.

## 10. Lifecycle state machine

Lifecycle state is harness-owned sidecar metadata, not a mutable packet field.

| Current state                   | Event                                                              | Required action                                        | Next state                |
| ------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------ | ------------------------- |
| none                            | Review yields valid findings or genuine empty result               | Create fresh packet and digest                         | `created`                 |
| none                            | No nonempty finding can fit                                        | Persist `packet_size` blocker                          | `refresh_required`        |
| `created`                       | All pre-invocation checks pass                                     | Bind digest to invocation                              | `validated`               |
| `created`                       | Snapshot or permission fingerprint differs                         | Skip attacker; persist stale diagnostic                | `refresh_required`        |
| `created`                       | Schema, digest, identity, duplicate, omission, or size check fails | Skip attacker; persist malformed diagnostic            | `refresh_required`        |
| `refresh_required`              | First stage-specific refresh validates                             | Supersede old packet                                   | `validated`               |
| `refresh_required`              | Stage-specific refresh fails or allowance spent                    | Record required-lane failure; no score effect          | `coverage_loss`           |
| `validated`                     | Attacker returns attacks                                           | Persist consumed digest and continue attack validation | `consumed`                |
| `validated`                     | Attacker returns `attacks: []`                                     | Mark downstream stages not applicable                  | `completed_empty`         |
| `validated`                     | Attacker returns valid blocker                                     | Persist blocker and use blocker-stage refresh          | `refresh_required`        |
| `validated`                     | Blocker persists or blocker refresh fails                          | Record required-lane failure; no score effect          | `coverage_loss`           |
| `created` or `validated`        | Repair, target mutation, policy change, or round end               | Make packet permanently non-consumable                 | `invalidated`             |
| `consumed` or `completed_empty` | Later repair, mutation, or policy change                           | Retain historical consumption; prohibit reuse          | terminal historical state |

Every transition records run, round, lane, packet ID and digest when available,
reason code, attempt number, and artifact pointers. No stale, malformed,
blocked, invalidated, or oversized packet can silently become `consumed`.

### 11.3 Stale target or permission fingerprint

If the current frozen patch hash is `99…99` while the packet attests `22…22`,
target recomputation fails with `packet_stale`; the attacker is skipped. If the
target matches but `postgres_test` expired after packet creation, its projected
status changes from `approved` to `expired`; permission recomputation also fails
with `packet_stale`, using diagnostic `permission_fingerprint_mismatch`. Both
failures consume the single pre-invocation refresh. A matching replacement
packet proceeds; another validation failure produces coverage loss.

### 11.4 Permission-related handoff blocker

The valid packet cites `postgres_test`, whose resolved role is
`harness_only`. The attacker cannot directly build the proposed fixture and
returns the blocker in section 8. No attack is accepted and no recoil applies.
The reviewer gets one blocker-stage refresh with the current policy. It may
rewrite the plan around a brokered harness check or omit the hypothesis. If the
fresh attacker blocks again, the lane has coverage loss.

### 11.5 Post-repair invalidation

Packet `P1` validates against tree `T1`. Before its attacker invocation, a
repair creates tree `T2`. The harness records `P1` as `invalidated`, even if the
patch is later reverted byte-for-byte to `T1`. Review runs again and creates a
fresh UUIDv7 packet `P2`; `P1` can only be displayed historically.

### 11.6 Duplicate findings

Priorities 1 and 3 normalize to the same canonical payload. Both compute the
same finding ID. Priority 1 remains in `findings`; priority 3 appears once in
`omitted_findings.entries` with `reason: "duplicate"` and `duplicate_of` equal
to that ID. Priority 2 is unaffected. The harness performs no semantic merge
with a differently worded finding.

### 11.7 Deterministic size compaction

After duplicate removal, a packet with priorities 1–12 serializes to 18,240
bytes. Removing priority 12 and recording its omission yields 17,010 bytes;
removing priority 11 and recording its omission yields 15,870 bytes. The final
packet contains priorities 1–10, two `packet_size` omissions ordered 11 then
12, and is accepted. Every implementation produces that same selection. If
priority 1 alone plus envelope and omission metadata exceeds 16,384 bytes, the
packet is blocked instead of silently becoming an empty success.

### 11.8 Malformed and oversized packets

A packet with an unknown field, a non-recomputing digest, a finding ID mismatch,
incorrect omission count, more than 12 retained findings, or more than 16,384
canonical bytes is `packet_malformed`. It is never injected. One
pre-invocation targeted review refresh is allowed; persistent failure causes
coverage loss without score effect.

## 12. Compatibility

V2 is the only supported handoff version. New runs, resumed work, artifact
readers, and runtime consumers MUST reject v1 packets. They MUST NOT read,
migrate, rewrite, upgrade, or consume v1 handoff artifacts. Existing generic
legacy-run support outside the reviewer-handoff feature remains unchanged.

## 14. Acceptance invariants

An implementation conforms only if all of the following hold:

- Every disclosed value has exactly one owner and an explicit trust label.
- All identities, fingerprints, finding IDs, omissions, and bytes validate
  deterministically before attacker invocation.
- Exact duplicates preserve the first-ranked occurrence; semantic duplicates
  remain for judge adjudication.
- Empty success cannot be confused with stale, blocked, malformed, oversized,
  missing, or post-repair handoff.
- The attacker can inspect focused target context without receiving reviewer or
  implementation transcripts or an embedded patch.
- No packet survives a round, repair, target mutation, or permission change.
- Handoff and telemetry failures never cause damage, recoil, healing, health,
  or selection changes; unresolved required lanes affect coverage only.
- Issues #18–20 can implement the contract without choosing additional product
  policy.
